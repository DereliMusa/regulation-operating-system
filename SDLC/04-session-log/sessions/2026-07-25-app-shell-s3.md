## What shipped

### Shared component logic (pure, unit-tested first)

To keep components presentational and the logic testable at the fast Node layer (per
[`../../02-standards/testing-strategy.md`](../../02-standards/testing-strategy.md)), the
badge/table/readiness logic lives in `app/utils/`:

- `app/utils/badges.ts` — one tone vocabulary (`approved | review | deficiency | draft`) for
  **every** status, GSPR conformity, and risk severity string in the app, plus the
  STYLE_GUIDE text/bg class pairs (`TONE_CLASS`) and solid fills (`TONE_SOLID`). Single source
  of truth so badge colors never drift. `statusTone`/`severityTone`/`statusLabel`/`severityLabel`.
- `app/utils/readiness.ts` — `clampPercent` (0-100, rounds, non-finite -> 0) and `ringGradient`
  (token-driven conic-gradient string; no hardcoded hex).
- `app/utils/table.ts` — `DataTableColumn` type + `resolveCellValue` (dot-path cell access).

Unit tests: `app/utils/__tests__/{badges,readiness,table}.test.ts` (14 assertions).

## Decisions

- **Badge tones are a single mapping** (`app/utils/badges.ts`), not per-component, so the
  three different status enums (technical-file / GSPR / risk) share one visual language.
- **No dead routes** (consistent with S8's marketing nav omitting Solutions/Pricing):
  every sidebar link resolves to a real (placeholder) page; **Settings / Support** render as
  **disabled** items (out of MVP scope) rather than links to nothing.
- **Slim app footer** — STYLE_GUIDE section 6 originally specced a full link footer inside
  the app; a link directory inside the authenticated app is mostly dead routes, so the app
  footer is slim (brand + copyright) and the full link footer stays in the marketing shell.
  STYLE_GUIDE section 6 updated to match (code/doc no-drift rule).
- **`vue/require-default-prop` disabled** (`eslint.config.mjs`): TypeScript optional props
  (`prop?: T`) already express "undefined when absent"; the runtime rule is redundant/noisy
  for TS-first components. Recorded in `coding-standards` intent; the config carries the why.

## Resolved

- **The S2 `/api/_*` auth open item is now confirmed in a real browser.** The previous
  session could not get the owner's manual retry confirmed. This session's headless-Chromium
  UI login (which exercises `useUserSession()`'s client re-check against `/api/_auth/session`
  — the exact endpoint that used to 401) succeeded and landed on `/dashboard`; the endpoint
  returns 200 both with and without a cookie. Treat as fixed. A final owner sanity click is
  welcome but no longer a blocker.

- **Correction / follow-up (same day):** the owner then tested login in their own browser and
  it still would not reach `/dashboard`. Root cause was a **separate** bug the Chromium check
  had masked: the session cookie is `Secure` by default, and Safari/Firefox refuse to store a
  `Secure` cookie over `http://localhost` (Chromium allows it on localhost). So my
  "confirmed in a real browser" above was Chromium-only and over-claimed. Fixed by making the
  cookie `secure` production-only (`runtimeConfig.session.cookie.secure` in `nuxt.config.ts`);
  dev `Set-Cookie` no longer carries `Secure`, login + session verified 200. Lesson: verify
  auth/cookie flows in a non-Chromium browser (or at least assert the `Set-Cookie` attributes)
  before calling a browser login "confirmed". See `architecture.md` auth section.

## Observations / not addressed (out of S3 scope)
